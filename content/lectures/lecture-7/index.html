The Network Was Built on Trust

  • TCP/IP was designed for a small research network where every operator knew every other operator. Authentication was not an omission — it was out of scope
  • Consequences we still live with:
    • A source IP address is a claim
    • An ARP reply is believed by whoever hears it
    • A DNS answer is accepted if it arrives first
    • A BGP announcement is accepted because a peer said so
  • Everything in this lecture is a patch over that original assumption

Passive: Listening

  • Sniffing — read traffic you can reach. Trivial on shared media and on any network you have a port on
  • Switches made it harder by accident, not by design: a switch forwards by MAC address, so you only see your own traffic
    • Until MAC flooding overflows the switch's address table and it fails open, broadcasting everything
  • The defence is not "stop them listening" — it is encryption, so that listening gains nothing. Lecture 1's rule for passive attacks: prevent, do not detect

Active: Lying

  • ARP spoofing — announce that your MAC address owns the gateway's IP. Every host on the segment believes you, and now you are the gateway
    • ARP has no authentication at all. There is nothing to break
  • DNS spoofing — answer the query before the real server does, or poison a resolver's cache so it lies to everyone behind it
  • IP spoofing — forge the source address. Easy for UDP; harder for TCP, which needs the sequence number
  • All three build the same thing: a machine in the middle

What the Middle Buys

  • Read everything · change everything · impersonate either side
  • Against plaintext this is total. Against TLS it is much less — the attacker can drop traffic, but cannot produce a certificate for the name
  • Which is why the attack shifted to stripping: keep the victim on http:// and there is no certificate to forge
  • And why HSTS from lecture 6 matters here — the browser refuses to be downgraded, so there is nothing to strip
  • Layer 2 answers exist too: dynamic ARP inspection and DHCP snooping on the switch, which drop the forged replies before anyone hears them

Denial of Service

Volumetric Fill the pipe. Measured in bits per second
Protocol Exhaust a state table — SYN flood. Measured in packets per second
Application Ask for the expensive thing. A few requests per second can be enough
  • Amplification is what makes the first one cheap: send a small query with a forged source, and the server sends a large answer to the victim
  • UDP services with no handshake are the reflectors — DNS, NTP, memcached. US-CERT TA14-013A tabulates the factors, and they run from tens to tens of thousands
  • You cannot absorb a volumetric attack on your own link. That defence is bought upstream

Reconnaissance

  • Before any of the above: what is here, and what is listening?
  • Host discovery, then port scanning, then banner grabbing to name the version, then a lookup of what that version is vulnerable to
  • On the public internet this is continuous and automated. A new address receives its first scan within minutes
  • Which reframes the defence: you cannot avoid being found, so reduce what is findable — the attack surface argument from lecture 1, applied to open ports

Zoning

  • A security zone is a group of systems with the same trust level and the same policy
  • Grouping by trust rather than by geography or department is the whole idea — a laptop in the building is not more trusted than one outside it
  • Traffic within a zone flows freely. Traffic between zones is controlled, inspected and logged
  • This is lecture 2's boundary drawing, made concrete in addresses and interfaces

The Classic Layout

Untrusted The internet. Assume hostile
DMZ Public-facing services. Reachable from outside, and trusted by nobody
Internal Workstations and internal applications
Restricted Databases, domain controllers, key material
Management Switch and hypervisor consoles, out-of-band cards. The keys to everything

The rule that gives the DMZ its value: a DMZ host must not be able to initiate a connection inward. Compromising the web server then buys the attacker one machine.

North-South and East-West

  • North-south — traffic crossing the perimeter. Historically where every control was placed
  • East-west — traffic between internal hosts. Historically unfiltered, unlogged, and far larger in volume
  • Which is exactly the path an intruder uses. Lateral movement is the phase between the first compromised laptop and the domain controller
  • A flat internal network means one phished user is equivalent to all of them
  • Microsegmentation pushes policy down to the individual workload, so east-west traffic gets the same treatment north-south always had

Zero Trust

Never trust, always verify. Location is not a credential.

  • The perimeter model assumes inside is safe. Remote work, cloud services and phones on the corporate wifi ended that assumption
  • Zero trust replaces it with per-request decisions:
    • Authenticate the user and the device, every time
    • Authorize the specific resource, not the network
    • Assume breach — design as though the attacker is already inside
  • NIST SP 800-207 is the reference. It is a direction, not a product, whatever the vendor says

What a Firewall Is

  • A choke point between two zones where a policy is enforced and traffic is logged
  • The value comes from being the only way through. A firewall with a route around it is decoration
  • And from default deny: permit what is needed, drop the rest. The opposite ordering is a list of things you happened to think of

Three Generations

Packet filter Each packet judged alone, by address and port. Fast, and cannot tell a reply from an unsolicited packet
Stateful Tracks connections, so replies are allowed and unsolicited packets are not. The baseline everywhere
Application layer Understands the protocol. A proxy terminates the connection and makes its own
  • Next-generation adds identity and application awareness, so a rule can say "the finance group may reach the ERP" rather than naming subnets
  • A WAF is an application-layer firewall for HTTP. It buys time to patch; it does not fix the code from lecture 6

Rules, and How They Go Wrong

  • Rules are evaluated in order, first match wins. A broad rule near the top silently shadows everything below it
  • The final rule is deny all, and it should log
  • Rule rot is the real failure: an "temporary" any-any rule from a migration three years ago that nobody dares remove
  • Review the rule base on a schedule, with an owner and a justification per rule
  • NAT is not a firewall. It hides addresses as a side effect of running out of them, and it is not a policy

Egress Filtering

  • Almost everyone filters inbound. Far fewer filter outbound, and that is where the detection value is
  • Malware has to call home; stolen data has to leave. Both are outbound connections from a host that has no business making them
  • A database server that suddenly opens an HTTPS connection to an unknown address is a high-quality signal — rare enough to beat the base-rate problem from lecture 5
  • Force outbound traffic through a proxy that authenticates and logs, and deny direct routes

Where Detection Sits

  • IDS observes a copy of the traffic and alerts. It cannot be a bottleneck and cannot stop anything
  • IPS sits inline and can drop. Which means a false positive is now an outage, and the device is a single point of failure
  • Placement decides what you see: outside the firewall shows you the internet's noise, inside shows you what got through. Inside is the useful one
  • And the modern limitation: most traffic is encrypted. Either you terminate TLS at a proxy — with all the trust and privacy questions that raises — or you inspect metadata and move detection to the host

Controlling Who Gets On

  • A network port in a meeting room is a connection to the internal zone, offered to anyone who sits down
  • 802.1X authenticates the device or user before the port carries any traffic
    • Supplicant (the client) → authenticator (the switch or access point) → authentication server (RADIUS)
    • Until it succeeds, the port passes nothing but the authentication exchange itself
  • NAC adds a posture check — patched, encrypted, running the agent — and can drop a failing device into a remediation VLAN
  • Port security on the switch limits how many MAC addresses a port may learn, which is the cheap answer to MAC flooding

VPN

  • A cryptographically protected tunnel across a network you do not control. It buys back confidentiality, integrity and peer authentication — the X.800 services, applied to a whole link
  • Two shapes, for two problems:
    • Site-to-site — two offices joined through routers. Users never know it is there
    • Remote access — one device joining from anywhere
  • What it is not: a defence against anything on either end. A compromised laptop on a VPN is a compromised laptop inside your network

IPsec

  • Security at the IP layer, so every protocol above it is covered
  • Two protocols, and only one is used:
    • AH — integrity and authentication, no encryption. Rarely deployed
    • ESP — encryption plus integrity. This is the one
  • Two modes, and the difference is what gets hidden:
    • Transport — protects the payload, leaves the original header. Host to host
    • Tunnel — wraps the entire packet in a new one, so the inner addresses are hidden too. Gateway to gateway
  • IKEv2 does the authentication and key agreement, and rekeys on a timer

The Other Options

IPsec Standard, interoperable, complex. The default for site-to-site
TLS VPN Runs over 443, so it crosses restrictive networks. OpenVPN and most vendor clients
WireGuard A few thousand lines, one fixed cipher suite, in the kernel. Small enough to audit
  • WireGuard's design choice is worth naming: it is not negotiable. No cipher negotiation means no downgrade attack and no misconfiguration
  • Split tunnelling — only some traffic goes through the VPN. Saves bandwidth, and bridges the internet to your internal network through the client

VLAN

  • One physical switch, several independent broadcast domains. Ports are assigned to a VLAN, and traffic between VLANs must pass a router
  • Which makes that router the choke point — VLANs are how zoning gets implemented without buying a switch per zone
  • 802.1Q adds a 4-byte tag carrying a 12-bit VLAN ID — so 4094 usable VLANs
  • Two kinds of port, and the distinction causes most VLAN incidents:
    • Access port — one VLAN, untagged. Where a host plugs in
    • Trunk port — many VLANs, tagged. Between switches

VLAN Hopping

  • Switch spoofing — the attacker's host pretends to be a switch and negotiates a trunk, receiving every VLAN
    • Fix: disable automatic trunk negotiation, and set every user-facing port to access mode explicitly
  • Double tagging — send a frame with two tags. The first switch strips the outer one and forwards it; the second reads the inner tag and delivers it to a VLAN the attacker cannot reach
    • It works because the native VLAN is carried untagged. Fix: make the native VLAN an unused one, and tag it
  • Note the direction — double tagging is one-way. Enough to attack, not to converse

What a VLAN Is Not

A VLAN is segmentation. It is not encryption, and it is not a firewall.

  • Traffic inside a VLAN is plaintext, and anyone on that VLAN can hear the broadcast domain
  • The separation is enforced by switch configuration — so it is exactly as strong as the switch's management access
  • Which is why the management zone exists: whoever reaches the switch console owns every VLAN on it
  • Private VLANs go further, isolating ports even within one VLAN — useful in a DMZ, where two web servers have no reason to talk to each other at all
