The Toolbox

  • Cryptography turns a security problem into a key management problem
  • That is a real win — key management is a problem we know how to work on
  • It is not a solution to anything by itself:
    • It cannot fix a program that trusts the wrong input
    • It cannot tell you who the key belongs to
    • It cannot help once the attacker is on the machine holding the key

Encryption is not magic dust. It moves the secret, and you have to know where to.

Words We Need

Plaintext The message, readable
Ciphertext The message, after encryption
Cipher The algorithm. Public, published, studied for years
Key The secret. The only secret
Cryptanalysis Breaking it without being given the key

Encryption gives confidentiality. Note what is missing from that sentence — everything else in this lecture is about the missing part.

Kerckhoffs's Principle

The system must remain secure even if everything about it, except the key, is public knowledge.

  • Auguste Kerckhoffs, 1883. Older than the computer, and never wrong yet
  • A key can be changed when it leaks. An algorithm cannot
  • Algorithms leak anyway — they are in the binary you shipped, and someone will disassemble it
  • Security through obscurity is the name for breaking this rule. It buys time, and it is never the plan

How the Old Ciphers Died

  • Caesar — shift each letter by k. 25 keys. Try all of them by hand
  • Substitution — an arbitrary permutation of the alphabet. 26! ≈ 288 keys, and still trivially broken
    • Because the key space is not the point: structure survives. `E` is still the most common letter, whatever you call it
  • Vigenère — a repeating key, which hides the frequencies until you find the period

The lesson lasts: a big key space is necessary and nowhere near sufficient.

How Big Is Big Enough?

Assume a machine testing 1012 keys per second:

240 about a second
256 (DES) about 20 hours
280 about 38 years
2128 (AES-128) far longer than the universe has existed
  • Beyond 128 bits, brute force stops being the thing to worry about
  • Every real break is a flaw in the design, the implementation, or the key handling — never the key length

The One Unbreakable Cipher

  • One-time pad: XOR the message with a truly random key as long as the message
  • Shannon proved it: with a random key used once, the ciphertext reveals nothing. Perfect secrecy, not "hard to break"
  • And it is useless in practice, for three reasons:
    • The key is as big as the data, and must be shared in advance
    • It must be truly random
    • Used twice, it collapses — XOR two ciphertexts and the key cancels out
  • Every stream cipher is an attempt to fake this, and the "never twice" rule follows it all the way

Symmetric Encryption

  • One key, shared. The same key encrypts and decrypts — conventional cryptography, and the only kind there was until 1976
  • Fast: gigabytes per second on a laptop, with hardware support
  • Its whole difficulty is in one question: how did both sides get the key?
  • n people who all want to talk pairwise need n(n−1)/2 keys. For 1,000 people that is 499,500

Block and Stream

  • Block cipher — encrypts a fixed-size block, e.g. 128 bits at a time
    • AES. Needs a mode to handle anything longer than one block
  • Stream cipher — generates a keystream and XORs it with the data
    • ChaCha20. Naturally handles any length, byte by byte
  • In modern practice the line is blurred: AES in counter mode is a stream cipher built from a block cipher

A Short History of the Standard

DES 1977, 56-bit key. Broken by dedicated hardware in 1998, in days. Dead
3DES DES three times, ~112-bit strength. Slow, 64-bit blocks. Disallowed by NIST
AES 2001, Rijndael, FIPS 197. 128-bit blocks, 128/192/256-bit keys. The answer
ChaCha20 The alternative, and faster where there is no AES hardware

AES was chosen through a public competition with published analysis — Kerckhoffs's principle applied to the selection process itself.

A Cipher Is Not Enough

  • AES encrypts 16 bytes. Your message is not 16 bytes
  • The mode of operation says how to chain the blocks — and it is where the security is actually won or lost
  • The obvious mode is to encrypt each block independently. That is called ECB, and it is the most instructive mistake in cryptography

Let us encrypt a picture with it.

Before

The raw pixels of this image, AES-128, one key, ECB mode.

After — This Is the Ciphertext

Every block is correctly encrypted with a strong cipher. Identical plaintext blocks produce identical ciphertext blocks, so the pattern survives.

The Same Image, CBC Mode

Same cipher, same key, same data. The only change is that each block is XORed with the previous ciphertext first.

Modes Worth Knowing

ECB Each block alone. Never use it. Ever
CBC XOR with the previous ciphertext. Needs a random IV; needs padding; padding is attackable
CTR Encrypt a counter, XOR with data. No padding, parallel, seekable
GCM CTR plus authentication. This is the default answer
  • CBC needs an IV and CTR/GCM need a nonce: not secret, but never repeated under the same key
  • Reuse a CTR/GCM nonce and you have reused a one-time pad. Two messages, one keystream, both readable

Hash Functions

  • Any input, fixed-size output. No key. Not encryption — there is nothing to reverse, because information was thrown away
  • Three properties, in increasing order of difficulty to achieve:
    • Preimage — given h, you cannot find any m with hash h
    • Second preimage — given m, you cannot find a different m′ with the same hash
    • Collision — you cannot find any pair that collides
  • Collisions are the easiest to attack — the birthday bound puts an n-bit hash at only n/2 bits of collision resistance

Which Hash?

MD5 Collisions since 2004, in seconds. Dead
SHA-1 Collision demonstrated 2017, chosen-prefix 2020. Dead
SHA-256 / SHA-512 The SHA-2 family. Fine, and everywhere
SHA-3 Different construction, kept as insurance against a break in SHA-2
BLAKE2 / BLAKE3 Fast, modern, well regarded

"Dead" still means dead where a deliberate collision matters — certificates, signatures, code updates.

From Hash to MAC

  • Lecture 1 left this open: a bare hash protects against accident, because anyone who rewrites the data rewrites the digest
  • Add a key. A Message Authentication Code can only be produced — and checked — by someone holding it
  • HMAC is the right construction, and the nesting is not decoration 

HMAC(K, m) = H( (K ⊕ opad) ‖ H( (K ⊕ ipad) ‖ m ) )

Naively hashing key ‖ message is broken against SHA-2 by length extension: an attacker who never learns the key can still append to your message and produce a valid tag.

Encryption Alone Is Not Integrity

  • A ciphertext you cannot read is still a ciphertext you can change
  • In CTR mode, flipping bit i of the ciphertext flips bit i of the plaintext. Exactly, predictably
  • So pay 100 to alice becomes something else of your choosing, without the key
  • The answer is authenticated encryption: confidentiality and integrity from one primitive, with one key
    • AES-GCM · ChaCha20-Poly1305 · AES-CCM
    • If you must combine them by hand, it is encrypt-then-MAC. The other orders have published attacks

AES-GCM, and One Flipped Bit


ct := gcm.Seal(nil, nonce, plaintext, nil)

out, err := gcm.Open(nil, nonce, ct, nil)
fmt.Printf("open as sent:   %q err=%v\n", out, err)

ct[3] ^= 0x01 // flip a single bit of the ciphertext
out, err = gcm.Open(nil, nonce, ct, nil)
fmt.Printf("open one bit flipped: %q err=%v\n", out, err)
    

plaintext  16 bytes  pay 100 to alice
ciphertext 32 bytes  e7cced5c...45ca5a1a
           the last 16 bytes are the authentication tag

open as sent:   "pay 100 to alice" err=<nil>
open one bit flipped: "" err=cipher: message authentication failed

Read the Output Again

  • 16 bytes in, 32 bytes out — the extra 16 are the authentication tag. Integrity costs space
  • The tampered open returned "", not garbage. It refused to produce a plaintext at all
  • That is the contract worth insisting on: no output before the tag verifies. An API that hands you unverified plaintext is an API that will be misused

The Problem Symmetric Crypto Cannot Solve

  • To send you an encrypted message I need a shared key. To share a key securely I need… an encrypted channel
  • For centuries the answer was couriers and codebooks. It does not scale to a web with billions of pairs of strangers
  • 1976, Diffie and Hellman: what if encryption and decryption used different keys, and only one of them had to be secret?

Two Keys, Two Directions

  • Everyone has a public key (published) and a private key (never shared)
  • What you get depends on which key you use
Encrypt with the public key only the holder of the private key can read it → confidentiality
Sign with the private key anyone can verify who it came from → authentication, non-repudiation

Same mathematics, opposite direction, completely different service. Confusing the two is the classic exam mistake.

Where the Hardness Comes From

RSA Factoring a large integer is hard. Encrypts, and signs
Diffie–Hellman Discrete logarithms are hard. Agrees on a shared key — does not encrypt
Elliptic curve The same problems over a curve, where they are harder per bit
  • None is proven hard. They are unbroken after decades of public effort, which is the strongest claim cryptography makes
  • A large quantum computer would break all three. Post-quantum standards (ML-KEM, ML-DSA) were published by NIST in 2024

Key Sizes Are Not Comparable

Security level Symmetric RSA / DH Elliptic curve
112 bits 3DES 2048 224
128 bits AES-128 3072 256
192 bits AES-192 7680 384
256 bits AES-256 15360 512

NIST SP 800-57. A 256-bit ECC key and a 3072-bit RSA key are the same strength — which is why everything new uses curves.

Nobody Encrypts Data With RSA

  • Public-key operations are thousands of times slower than AES, and RSA cannot encrypt more than its key size anyway
  • Hybrid encryption is what actually runs:
    1. Generate a random symmetric key for this message
    2. Encrypt the data with AES-GCM under that key — fast
    3. Encrypt the key with the recipient's public key — small
  • TLS, PGP, Signal, encrypted disks: all the same shape. Public key to move a key, symmetric key to move the data

Forward Secrecy

  • If the session key is encrypted to a long-lived public key, then whoever recorded the traffic today can decrypt all of it the day that private key leaks
  • Instead, agree a fresh key per session with ephemeral Diffie–Hellman, and use the long-term key only to sign the exchange
  • Now the private key proves identity but decrypts nothing. Yesterday's recording stays unreadable
  • This is why TLS 1.3 removed static-RSA key exchange entirely: it made forward secrecy non-optional

Digital Signatures

  • Hash the message, then transform the hash with the private key
  • Hashing first is not an optimization — it is what lets a fixed-size operation sign a message of any length
  • Anyone with the public key can verify. Nobody else can produce one
  • Algorithms: RSA-PSS · ECDSA · Ed25519

A signature over a broken hash is a broken signature — which is precisely why SHA-1 mattered.

Sign, Verify, Tamper


$ openssl genpkey -algorithm ed25519 -out priv.pem
$ openssl pkey -in priv.pem -pubout -out pub.pem
$ openssl pkeyutl -sign -inkey priv.pem -rawin -in msg.txt -out msg.sig
sig bytes: 64

$ openssl pkeyutl -verify -pubin -inkey pub.pem -rawin \
      -in msg.txt -sigfile msg.sig
Signature Verified Successfully

$ openssl pkeyutl -verify -pubin -inkey pub.pem -rawin \
      -in msg2.txt -sigfile msg.sig      # one character added
Signature Verification Failure

64 bytes, for a message of any size.

MAC or Signature?

MAC Signature
Keys one, shared a key pair
Who can verify anyone who can also forge everyone, and only the owner can sign
Non-repudiation no yes
Speed very fast much slower

Both give integrity and origin. Only the signature settles an argument — with a MAC, either party could have produced the tag, so neither can prove the other did.

Whose Public Key Is It?

  • Everything above assumed you have the right public key
  • If an attacker can hand you their public key while claiming to be the bank, every signature verifies perfectly — for the wrong party
  • Cryptography cannot answer this. It is a trust question, and it needs an outside answer

Public-key cryptography does not remove the need to distribute something securely. It reduces it to distributing something public.

Certificates

  • A certificate is a signed statement: "this public key belongs to this name"
  • Signed by a Certificate Authority
  • An X.509 certificate carries, at minimum:
    • Subject — the name it is about
    • The subject's public key
    • Issuer, validity dates, allowed uses
    • The CA's signature over all of it
  • Your trust in a website is a chain: leaf → intermediate → root, and the root is preinstalled in your OS or browser

The Chain Has Consequences

  • Your browser trusts a few hundred roots. Any one of them can issue a certificate for any name
  • DigiNotar, 2011 — a compromised CA issued a valid certificate for *.google.com, used to intercept Iranian users. The CA was distrusted and went bankrupt
  • The patches are structural, not cryptographic:
    • Certificate Transparency — every issued certificate is logged publicly, so misissuance is visible
    • CAA records — the domain owner names which CAs may issue for it

Revocation Is the Hard Part

  • A private key leaks on Tuesday. The certificate is valid until next year
  • CRL — a list of revoked serial numbers. Large, and stale between fetches
  • OCSP — ask the CA about one certificate. Adds a round trip, leaks your browsing to the CA, and clients fail open when it times out
  • A check that is skipped whenever it fails is not a check
  • The direction that actually worked: short-lived certificates. Ninety days, then forty-seven — expiry does the job revocation could not

Keys Have a Life Cycle

  • Generate — from a real CSPRNG. Weak randomness has broken more keys than cryptanalysis
  • Store — in an HSM, a KMS or the platform keystore. Not in the repository, not in an environment variable if you can help it
  • Distribute — the problem certificates exist to solve
  • Rotate — on a schedule, so that rotating is a rehearsed operation and not an emergency
  • Destroy — and remember the backups, the snapshots and the old images

One key, one purpose. A key that both signs and encrypts turns any flaw in either into a flaw in both.

Rules That Will Serve You

  • Do not implement it. Use a reviewed library, at the highest level it offers
  • Authenticated encryption by default — AES-GCM or ChaCha20-Poly1305
  • Never reuse a nonce under one key
  • Randomness from the OS — crypto/rand, not math/rand
  • Compare secrets in constant time — an early-exit comparison leaks the answer through timing
  • Keep the key and the data apart, and know where each one lives

The cipher is almost never what fails. The way it was used is.
