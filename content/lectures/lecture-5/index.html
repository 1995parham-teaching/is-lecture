One Machine, Many Tenants

  • An operating system exists to let mutually distrusting programs share one machine. That is a security job before it is a convenience
  • Everything rests on a hardware boundary the software cannot talk its way past: user mode and kernel mode
  • A user-mode program cannot touch another process's memory, a device, or the page tables. It can only ask, through a system call
  • The system-call boundary is therefore the most attacked interface on the machine

Trusted Computing Base

  • The TCB is everything that has to be correct for the security policy to hold
  • Kernel, drivers, firmware, the bootloader, every setuid binary
  • A bug inside the TCB defeats the policy. A bug outside it does not — that is the entire reason for drawing the line
  • So: keep it small. A driver from an unknown vendor is in your TCB with full kernel rights

Lecture 2 called this "trusted functionality" and told you to keep it small. This is what it looks like in practice.

The Reference Monitor

  • The idealised access-control enforcer. Three requirements:
    • Complete mediation — every access goes through it, with no side door
    • Tamper-proof — nothing it governs can modify it
    • Verifiable — small enough that it can be analysed
  • Real kernels approximate all three and achieve none exactly, which is why the rest of this lecture exists

Hardening

  • Patch. The overwhelming majority of compromises use a vulnerability that had a fix available
  • Remove. Uninstall what is not used; disable the services that start by default
  • Separate. One service per account, none of them root
  • Default deny on the host firewall, inbound and outbound
  • Measure. A benchmark you can re-run — the CIS Benchmarks exist for exactly this

Unglamorous, and it beats every product you could buy instead.

The File System Is the Database

  • Configuration, credentials, keys, logs and the data itself all live in one namespace governed by one mechanism
  • Lecture 4 gave the model. Here it is the operational detail:
    • Sensitive files should be 0600, owned by the service account
    • Directories need x to traverse — a permissive parent undoes a strict child
    • Audit setuid binaries. Each one is a place a local user becomes another user
  • The mistakes that recur: a world-readable key, a backup written with the wrong umask, a config committed to git

Encryption at Rest

  • Full-disk encryption — FileVault, LUKS, BitLocker. Protects against the stolen laptop and the discarded disk
  • Be precise about what it does not do: once the machine is running and unlocked, every file is readable by anyone who is on it. It defends a powered-off device
  • File- or field-level encryption narrows the window further, at the cost of key management in the application
  • The key has to live somewhere: a TPM or secure enclave, released to the boot process — not a passphrase in a script beside the disk

Knowing When It Changed

  • File integrity monitoring: hash the files that should never change, and compare on a schedule
  • Binaries, configuration, cron jobs, startup scripts, the web root
  • The baseline has to be stored where the attacker cannot reach it, or they will update it along with the file — the lecture 1 problem again
  • Tripwire and AIDE do this. So does a package manager verifying its own database, which most systems already have

Malware, Sorted

Sort by how it spreads, not by what it does:

Virus Attaches to a host file. Needs a user to run it
Worm Self-propagating over the network. Needs nobody
Trojan Useful-looking, and the user installs it deliberately
Rootkit Hides the others, usually by lying to the kernel
Bot Waits for orders from a command-and-control server

Then, separately, the payload: ransomware, spyware, a miner, a wiper, a keylogger. Any spreader can carry any payload.

Why the Worm Is Different

  • Everything else moves at human speed. A worm moves at network speed
  • Morris, 1988 — a few thousand hosts, and it took down a noticeable fraction of the internet that existed
  • Slammer, 2003 — a single UDP packet, no disk footprint, doubling every 8.5 seconds
  • WannaCry, 2017 — ransomware payload on a worm spreader, using a leaked SMB exploit. A patch had been available for two months
  • The defence is not detection. It is patching and segmentation — nothing human is fast enough to respond

Ransomware, Because It Is What You Will Meet

  • Encrypt the victim's files, sell the key. Purely a business model
  • It is good cryptography used against you — asymmetric, so the key you need was never on your machine
  • The modern version is double extortion: the data is exfiltrated first, so paying nothing means publication and paying anyway means trusting a criminal
  • The attack targets your backups first, because it knows that is the defence
  • Which makes the lecture 2 rule the technical control that matters here: one copy offline or immutable

Detecting It

  • Signature — match known bytes. Exact, and useless against anything new
    • Defeated by polymorphic malware, which re-encrypts itself per copy, and metamorphic, which rewrites its own instructions
  • Heuristic — suspicious structure. Catches variants, and raises false alarms
  • Behavioural — watch what it does when it runs. Enumerating and encrypting every document is hard to disguise, because it is the goal
  • Sandbox — run it somewhere disposable first. Malware checks whether it is in one, so this is an arms race

The Oldest Bug

  • C will happily write past the end of an array. Nothing checks, because checking costs a cycle
  • The bytes past the end are not empty. They are the next thing in memory
  • So the attacker's input stops being data and starts being state — which is lecture 6's rule, one layer down 

struct session {
  char name[16];
  int  is_admin;      /* the next field in memory */
};

Sixteen Bytes Is Sixteen Bytes


struct session s;
s.is_admin = 0;
strcpy(s.name, argv[1]);            /* no bound check */
printf("name=%-24s is_admin=%d\n", s.name, s.is_admin);
    

$ ./login parham
name=parham                   is_admin=0

$ ./login AAAAAAAAAAAAAAAAAAAA
name=AAAAAAAAAAAAAAAAAAAA     is_admin=1094795585

1094795585 is 0x41414141 — four of the letter A. The name overflowed straight into the flag.

And With a Little Aim


$ ./login "AAAAAAAAAAAAAAAA$(printf '\x01')"
name=AAAAAAAAAAAAAAAA        is_admin=1
  • Sixteen bytes of filler and one chosen byte. The program is now an administrator
  • Nothing was hacked. strcpy did exactly what it is documented to do
  • On the stack the interesting neighbour is not a flag but the return address — overwrite that and you choose where the function returns to

The Same Source, Compiled Defensively


$ cc -O0 -o login-hardened login.c        # the defaults
$ ./login-hardened AAAAAAAAAAAAAAAAAAAA
exit=133          # SIGTRAP — __strcpy_chk knew the buffer was 16 bytes

$ cc -O0 -fstack-protector-all -o login-canary login.c
$ ./login-canary AAAA…40 bytes
exit=134          # SIGABRT — the canary was overwritten
  • Not one line of the program changed. The compiler did the work
  • Both mitigations turn a silent privilege escalation into a crash — which is a denial of service, and an enormous improvement

Layers of Mitigation

Stack canary A random value before the return address, checked on return
NX / DEP Writable memory is not executable, so injected bytes cannot run
ASLR Randomize the layout, so the attacker cannot name an address
FORTIFY_SOURCE The compiler knows the buffer size and checks at run time
CFI Indirect calls must land on a legitimate target
  • Each raises the cost; none is a fix. NX produced return-oriented programming, which builds the payload out of code already in the binary

The Actual Fix

  • Use a memory-safe language where you can. Go, Rust, Java, Python — the bug class simply does not exist
  • Microsoft and Google have both reported that around 70% of their severe vulnerabilities were memory-safety issues. Independently, in different codebases
  • Where C is required: bounded functions, sanitizers in CI (-fsanitize=address,undefined), fuzzing, and review of every allocation
  • And the same discipline as everywhere else — validate at the boundary, and never trust a length that came with the data

The Host Firewall

  • The network firewall of lecture 7 protects a zone. This one protects the machine, and it is the one that still works when the attacker is already inside the zone
  • Inbound: default deny, then allow the ports this host actually serves
  • Outbound matters more than people expect. Malware has to reach its command-and-control server; a compromised database server has no business opening connections to the internet
  • pf, nftables, Windows Defender Firewall — the rules differ, the discipline does not

Host-Based Intrusion Detection

  • A HIDS sees what the network cannot: which process, which user, which file, which syscall — and it sees it after decryption
  • A NIDS sees the whole segment from one place, and is invisible to the host it is watching
  • They are complements, not alternatives
  • Two detection strategies, with opposite failure modes:
    • Misuse — match known-bad. Precise; blind to the new
    • Anomaly — model normal, alert on deviation. Can catch the new; buries you in false alarms

Why "99% Accurate" Is Not Good News


events/day               1,000,000
  of them, attacks             100
detection rate               99.0%
false-alarm rate              0.1%

true  alarms/day                99
false alarms/day             1,000
total alarms/day             1,099

P(attack | alarm)            9.01%

A detector that misses almost nothing, and nine out of ten alarms are wrong.

The Base-Rate Fallacy

  • When the thing you are looking for is rare, the false-alarm rate dominates — however good the detector is
  • This is why analysts stop reading alerts, and why the alert that mattered was in the queue all along
  • What actually helps:
    • Raise the base rate — watch a narrower, higher-value population rather than everything
    • Correlate — require two weak signals, so the false-positive rates multiply
    • Drive the false-alarm rate down, even at the cost of detection. 0.01% would change the table above tenfold

Isolation You Can Buy

  • A hypervisor runs several operating systems on one machine, each believing it has the hardware
    • Type 1 — on the bare metal. ESXi, Hyper-V, KVM. Small TCB, and what clouds run
    • Type 2 — on top of a host OS. VirtualBox, VMware Workstation. The whole host OS joins your TCB
  • For security the appeal is simple: a compromised VM is a compromised VM. The blast radius has a wall around it
  • And snapshots make analysis cheap — run the malware, look, roll back

The Wall Has Doors

  • VM escape — a bug in the hypervisor, usually in an emulated device, that gets code onto the host. Rare, and total
  • Side channels — shared caches and shared branch predictors leak between tenants. Spectre and Meltdown were about exactly this
  • Sprawl — a VM that is off is not being patched, and it comes back months out of date
  • The management plane is the real target. Whoever holds the hypervisor console holds every guest, and the console is protected by a password

Containers Are Not Small VMs

  • A container is one kernel, partitioned by namespaces and cgroups. There is no second operating system
  • So a kernel vulnerability is shared by every container on the host, while a VM would still have a hypervisor between them
  • Weaker isolation, far lower cost. Both are correct answers to different questions
  • If you run them: non-root user, read-only root filesystem, dropped capabilities, a seccomp profile, and never --privileged
  • Where the boundary must be strong, put a real one back: Firecracker, Kata, gVisor

Where This Leaves Us

  • The host is defended by the boring things: patch, minimise, separate, log
  • The bug classes that survive are the ones where data crossed into control — a buffer into a flag, a file into a privilege
  • Isolation limits the damage; it never prevents the bug
